## H-1 — Anyone can forge "funded from Bitcoin" on any MUSD tip
**File:** `lib/server/funding.ts` `verifyFunding`, `recordFundingClaim`; `lib/server/tips.ts` `submitTip` · **Confidence:** 100 (PoC)

**Description:** The funding check accepts any router call, never reads the amount or the funding sender, allows one funding tx for unlimited tips, and any caller can attach the claim.

Five gaps combine:
1. **Direct router call skips the selector.** For a direct router call the selector argument is `null`: `callsTarget(tx, router, lc(tx.to) === lc(router) ? null : FUNDING_SELECTORS.swap)`, so any router call passes. The route's input token is never decoded, so it is never checked as BTC.
2. **Nested check is a byte match.** The smart-account branch only looks for the router address and the selector bytes somewhere in the input. A 1-wei `MUSD.transfer(victim, 1)` with `router ++ 0xcac88ea9` appended passes.
3. **Amount never compared.** The funded MUSD amount is never compared with `amount_raw`.
4. **Funding tx reusable.** There is no unique index on `tips.funding_tx_hash`.
5. **Anyone can attach the claim.** `tx.from` is never compared with the tip sender. `POST /api/tips/{id}/submit` needs no session, and tip ids and hashes are public (`/api/creators/{u}/tips`, the Explore feed). `recordFundingClaim` has no status check, so it also overwrites a pending, honest claim.

**Proof:** agent 6's PoC: one 0.01 MUSD funding tx with input `0xdeadbeef` to the router → three 1,000 MUSD tips all `funding_verified = TRUE`. The "funded from Bitcoin" count is the headline Mezo metric on dashboards and Explore.

**Fix:**
- Decode `swapExactTokensForTokens`: require `routes[0].from == BTC_TOKEN`, last hop `to == MUSD`, and `to == sender`. Remove the `null`-selector branch.
- Require `tx.from` (or, for smart accounts, the account) to equal `sender`, and the MUSD received to be at least `amount_raw`.
- Add `CREATE UNIQUE INDEX … ON tips (chain_id, funding_tx_hash) WHERE funding_tx_hash IS NOT NULL`.
- Accept a funding claim only on the first submit, before the tip is confirmed.

## H-2 — Anonymous tips leak the supporter's wallet and message
**File:** `lib/server/tips.ts` `toTipView` (+ `x402/record.ts` `loadX402TipView`), `lib/server/creators.ts` `getPublicTips` and `getPublicCreator` stats, `lib/server/dashboard.ts` `toDashboardTip`, `lib/server/indexer.ts` step 3 · **Confidence:** 100 (PoC)

**Description:** Public endpoints return anonymous supporters' addresses and messages, despite the tip form's promise "Your name and wallet won't be shown on this page."

**Proof:**
- `GET /api/tips/{id}` has no auth and returns `senderAddress` and `message` for anonymous tips. The PoC output shows `isAnonymous=true … senderAddress=0x3c52…`.
- `getPublicTips` has no `is_anonymous` filter, unlike `social.ts`. It lists anonymous tips with `id`, `txHash` and `message`, which makes the first leak reachable and points to the explorer.
- The creator dashboard shows anonymous messages.
- Public stats count anonymous senders.
- A payment that mines after its anonymous intent expired or timed out is recorded by the indexer as a **public** tip with the wallet shown.

**Fix:**
- Return `senderAddress` and `message` as `null` when anonymous in `toTipView` and `loadX402TipView`.
- Add `AND NOT is_anonymous` to `getPublicTips` and to the public stats.
- In step 2, match expired or timed-out intents by ref and carry over their `is_anonymous`, name and message.

## M-1 — Indexer counts non-tips as supporter tips
**File:** `lib/server/indexer.ts` `handleTransfer` step 3; `lib/server/tips.ts` `createTip`

**Description:** Any MUSD/MEZO transfer ≥ 0.01 to a creator wallet becomes a confirmed tip with `sender = log.from`, and the sender is never checked. This means:
- a creator's self-transfers count as tips;
- dust from fresh sybil wallets counts, at 0.01 MUSD plus gas per supporter;
- **Mezo loan mints** (`Transfer(0x0 → W)` from openTrove or withdrawMUSD) show up as a 1,800 MUSD tip from `0x0000…`;
- router swap outputs show the pool as the supporter.

Explore ranks creators by distinct supporters. `createTip` also accepts `senderAddress == recipient`.

**Fix:**
- Ignore transfers whose `from` is the zero address or any wallet of the same creator.
- Record indexer tips only when `tx.to` is the token contract.
- Reject self-tips in `createTip`.
- Consider counting only intent-linked tips in supporter totals.

## M-2 — Copied tip ref lets an observer fail a tip or take its name
**File:** `lib/server/indexer.ts` `handleTransfer` step 2; `lib/server/verify.ts` `verifyTip`

**Description:** Step 2 binds an open intent to any transfer whose calldata carries its ref. It checks no sender, no amount and no token, and the ref lookup ignores `token_address`.

**Proof:** An observer who sees the pending tx copies the ref:
- **0-value transfer:** the intent fails with `amount_mismatch`/`calldata_mismatch`, and the supporter's own submit then gets `tip_closed`. The supporter loses their name and message and may pay twice.
- **Exact amount:** the victim's name and message attach to the observer's address.
- **Across tokens:** a MUSD transfer carrying a MEZO intent's ref fails that intent, because MUSD is indexed first.
- **Smart-account variant:** `fail(..., releaseHash=false)` on `amount_mismatch` keeps the hash bound, so the creator's real transfer in that tx is never credited.

**Fix:**
- In step 2, bind only when the calldata equals the intent's expected calldata (or contains it, for smart accounts), `t.value == expected_amount_raw`, `token_address` matches, and, when the intent claimed a sender, `t.from` matches it.
- Never mutate an intent on a non-matching transfer.
- Release the hash on `amount_mismatch` and `no_matching_transfer`.

## M-3 — Unthrottled polling and dust floods
**File:** `app/api/tips/[id]/route.ts` GET, `app/api/health`, `lib/server/indexer.ts` `handleTransfer` / `processChunk`

**Description:** RPC load and indexer stalls can be driven at will.
- **Polling:** `GET /api/tips/{id}` has no rate limit, and every open tip re-verifies on chain every 3 s. One IP can hold hundreds of submitted tips with random hashes, about 400 RPC calls/s. `/api/health` is also unlimited.
- **Dust floods:** each dust transfer costs an `upsertEvent`, DB reads and a `getTransaction` RPC **before** the dust check. The cursor advances only after the whole 2,000-block chunk, so a flood can push a cron run past `maxDuration = 60` and replay the same chunk forever.

**Fix:**
- Add a per-IP `rateLimit` to GET `/api/tips/[id]` and `/api/health`.
- Verify that a tx exists before binding a hash.
- Move the dust check above `upsertEvent`/`getTransaction`.
- Commit the cursor per bounded batch.

## M-4 — Lookalike usernames pass the reserved check
**File:** `lib/usernames.ts` `usernameProblem` · verified: `official_mezo`, `mezo_foundation`, `support_tipmusd` → `null` (allowed); only brand-first forms such as `mezo_official` are blocked.

**Description:** An impostor can register a Mezo-looking tip page and receive payments meant for Mezo. Display names have no brand check either.

**Fix:**
- Reserve any username that contains `mezo|tipmusd|musd` together with a role word (official, team, support, admin, help, foundation, labs, network), in either order, after stripping `_`.
- Apply a softer check to display names.

## M-5 — Stale payout wallet on open intents
**File:** `lib/server/profiles.ts` `changePayoutWallet`, `lib/server/tips.ts` `submitTip`, `verify.ts`

**Description:** An intent snapshots `recipient_address` when it is created. After a payout change, open intents still pay and confirm to the **old** wallet for up to 30 minutes. `expires_at` is only enforced by the sweep.

**Fix:**
- Expire the creator's open intents inside the `changePayoutWallet` transaction.
- Reject expired intents in `submitTip` and in indexer step 2.

## M-6 — Fund-from-Bitcoin signs a re-quoted amount; stale funding carries over
**File:** `components/tip/fund-from-bitcoin.tsx` `run`, `components/tip/tip-flow.tsx` `restart`

**Description:**
- **Re-quote:** at click time, `run()` re-quotes and signs `plan.amountIn` (swap) or `plan.coll` (loan) without comparing it with the amount on screen. A price move means the supporter approves more BTC than shown. The wallet shows the real value, but the UI never asks again.
- **Stale funding:** `restart()` does not clear `funding`, so the next tip is submitted with the previous tip's funding claim.

**Fix:**
- If the fresh amount is more than the displayed one (beyond a small bound), stop and ask the supporter to confirm again.
- Reset `funding` on restart, and whenever the amount or token changes.

## Low

- **L-1 · `indexer.ts` step 1 — multi-transfer-tx-dropped.** The unique index allows one tip per tx hash, so a second creator transfer in the same transaction is dropped. This includes MUSD and MEZO sent in one smart-account batch. *Fix:* key indexer tips on `(tx_hash, log_index)`.
- **L-2 · `tips.ts` `createTip` / `dashboard.ts` — unverified-sender-shown-as-supporter.** The client-set `senderAddress` and name show on the creator dashboard (in the recent list and pending count) for intents that never paid. *Fix:* show the sender and name only after the verifier sets them from the log.
- **L-3 · `events.ts` — analytics-visitor-key-client-controlled; `ratelimit.ts` window burst.** The User-Agent is part of the visitor hash, so one IP can add about 60 "unique visitors" per minute. The fixed-window limiter also allows twice the limit at each window edge.
- **L-4 · `tips.ts` `createTip`, `x402/record.ts` — name stored when messages are off.** Only `message` is checked against `messagesEnabled`; `supporterName` is stored and shown publicly.
- **L-5 · `fund-from-bitcoin.tsx` — loan disclosure.** The consent text shows the rounded principal, not total debt (fee + 200 MUSD gas compensation), and shows no liquidation price.
- **L-6 · `profiles.ts` / `indexer.ts` — suspended creators.** A suspended creator can still change their payout wallet, and their transfers are still indexed.
- **L-7 · `tip-flow.tsx` / `tips.ts` — late wallet confirmation.** A wallet that confirms just after the 30-minute intent expires records the tip without its name or message.
- **L-8 · `auth.ts` — sign-in nonce not bound to the browser.** A creator phished into signing the real sign-in message hands over a session, which can then change the payout wallet with only the new wallet's signature. *Fix:* bind the nonce to an HttpOnly cookie set by `/api/auth/nonce`. Consider requiring the current wallet's signature for a payout change.

## Leads (unverified; worth a look)

- **Proxy headers:** `clientIp` trusts the first `X-Forwarded-For` hop when `x-real-ip` is missing, and `checkOrigin` trusts `X-Forwarded-Host`. Both depend on the hosting proxy.
- **Indexer scale:** above 500 creator wallets, `getLogs` drops its topic filter.
- **Reorgs:** a rewind keeps `funding_verified` and ignores x402 tips. The reorg check reads only the cursor block hash.
- **x402:** the `name`, `message` and `anonymous` fields are not covered by the signed payment. The Permit2 approval is MAX. Raw facilitator error text is returned to clients.
- **Request handling:** `parseBody` buffers the whole body before the size check. The session secret falls back to a dev constant if `NODE_ENV` is unset.
- **Client edge cases:** a zero oracle price makes `collForDebt` divide by zero during render. The recovery-mode borrowing fee is assumed to be 0. The send button rounds the amount to 2 decimals.
- **Catch-up slot:** any session can hold the global 15 s catch-up slot.
- **Smart-account verification:** this branch matches calldata by substring and does not tie the Transfer log to that call. Passport batch behavior hasn't been verified.

## Suggested fix order
1. **H-1:** funding verification and claim authorization.
2. **H-2:** anonymous-tip privacy.
3. **M-1 and M-2:** indexer sender, mint and ref-binding rules.
4. **M-3:** rate limits and the dust check ordering.
5. **M-4 to M-6.**
6. **Lows.**

Every fix needs a regression test in `tests/server` (most can extend `tests/server/v2.test.ts`).
